## 2026-11-26 · 多 Agent 协作与 v5 架构启动

### 1. 「遇冲突即停 + 结构化 A/B 选项与推荐」是最省返工的协作协议
- **发生了什么：** Dot 在 `dot/v5-phase1a` 动工前及 Task 4 前，先后通过 `PLAN-ISSUES.md` 拦下 3 处冲突：`authorized → go` 之间崩溃与已运行后退出的区分、`rusqlite` 无独立 `fts5` feature、v4 旧测试（取消冻结/复用旧 worktree）与 v5 Attempt 隔离的冲突，并给出带推荐项的 A/B 选项。
- **根因：** 实施计划在跨大版本迁移时未预先列出“旧测试语义变更白名单”，且部分底层边界（如 `authorized → go` 窗口）只有在真正写代码/跑校验时才会暴露。
- **流程改进：** 后续编写跨版本实施计划时，显式附上「旧测试语义变更白名单」；执行 Agent 遇到计划未授权的冲突时继续坚持“停下 → 写证据 → 给 A/B 选项与推荐”。
- **反哺 Polyclave 设计：** 阶段 1B 可为 Worker 新增结构化 MCP 工具 `raise_plan_issue({ level: 'detail' | 'direction', evidence, options, recommendation })`，`detail` 级由主控 `hub` 自动裁决放行，`direction` 级才弹窗请用户拍板。

### 2. 设计稿、规范文字与无头渲染预览的三方漂移
- **发生了什么：** 核查 `polyclave-v5-desktop-ui.fig` 时发现：底层线性渐变漏设垂直方向矩阵导致全局底部极光出现水平切线；`Deepy` 像素蓝鲸本身无脚，但规范文字笼统写成了“4 细腿”；Node 无头 CanvasKit 渲染因未注册系统 CJK 字体而隐藏了中文节点。
- **根因：** 视觉稿、设计文档和无头截图工具各自独立演进，缺少一步交叉核对。
- **流程改进：** 每次修改设计稿或规范后执行“图层 ↔ 规范文字 ↔ 实施计划”三方交叉核对；涉及中文字体视觉验收时，直接用原生桌面工具（OpenPencil）目视终审，不以无头截图作为唯一依据。
- **反哺 Polyclave 设计：** 阶段 1B 的无头浏览器验收门禁必须实测中文字体渲染与全局视口连续性，不能仅靠 DOM 断言。

### 3. 多 Agent 并行推进时的「零冲突分支纪律」
- **发生了什么：** Dot 在 `dot/v5-phase1a` 上实施阶段 1A 底座期间，我们在本地 `main` 补充了阶段 3（`google/agentmesh`）、阶段 4（社区工作流蒸馏）设计及经验库，但刻意不触碰 1A 计划文件且暂缓推送 `main`。
- **根因：** 若在执行 Agent 拉出工作分支后频繁往 `main` 推送或改动其正在执行的计划文件，会制造无谓的 rebase/merge 冲突。
- **流程改进：** 分支执行期间，`main` 只做不重叠的远期文档演进并暂留本地；待分支审查合并后再统一合流推送。
- **反哺 Polyclave 设计：** 主控 `hub` 同时调度多个 Worker 时，对同一仓库的共享契约/文档变更应串行化或在独立整合窗口合流。

### 4. 「云端确定性闭环 + 本机实机门禁」的分层验证
- **发生了什么：** Dot 在云端 Linux 环境跑通了确定性离线测试与 macOS/Windows 交叉编译及 Clippy，同时明确标注真实双平台运行与 `POLYCLAVE_REAL_CODEX/CLAUDE` 探针需留待本机合并审查时实跑。
- **根因：** 云端分支执行环境缺乏用户本机真实 CLI 登录态与双平台真机环境，硬凑反而容易引入虚假 mock 或泄露凭据。
- **流程改进：** 明确分层验收边界：分支执行 Agent 负责确定性离线闭环与 CI 编译/静态检查；合并审查者负责本机双平台实跑、真实 CLI 探针与 UI 实测。
- **反哺 Polyclave 设计：** 与 Polyclave “Worker 在 `network_access=false` 沙箱跑确定性闭环，宿主在可信本机执行 R1 核证与最终门禁”的架构完全一致。

## 2026-11-27 · `main@3dec8e4` 全项目审查

### 5. 测试全绿，但测试夹具自己伪造了生产环境里不存在的前提
- **发生了什么：** PR 门禁（`pr_gate.rs`）推送的是 `refs/polyclave/runs/<runId>/final`。生产代码里没有任何地方创建这个 ref，R1 验收写的是 `refs/heads/polyclave/<runId>`。只有测试 `hub_api/tests.rs` 手工推了 `final`，所以离线测试、macOS 和 Windows CI 全部通过，真实运行时第一次推送就会失败。
- **根因：** 端到端测试的前置状态由测试自己手工搭出来，没有走生产代码的产出路径。两个模块之间的约定（ref 名）因此只在测试里成立。
- **流程改进：** 凡是跨模块交接的前置状态（ref、表记录、文件），测试都要调用生产函数来产生，不能手写。审查时专门搜一遍：测试里出现的字面量 ref、路径或键名，生产代码里有没有对应的写入方。
- **反哺 Polyclave 设计：** 门禁推送的应该是已核验的确切 SHA（`<sha>:refs/heads/<branch>`），推送后再核对远端分支顶端，而不是推送一个"应该指向它"的 ref 名。

### 6. 兜底分支悄悄绕过了核心不变量
- **发生了什么：** 返工执行器返回 `run.result_sha.or(run.observed_sha)`。R1 没有接受结果时，它退回到"观察到的 SHA"，于是未经核验的提交可能被送去评审，甚至被批准。同一批代码里，Reviewer 用的是 `git show <head>`，只看到最后一个提交；diff 超过 24 KB 被截断时，模型也不知道。
- **根因：** 为了"总能拿到一个 SHA"或"别让提示词太长"而写的兜底，没有对照 R1 去检查。测试只覆盖正常路径，从没构造过只有 `observed_sha` 或多提交的情况。
- **流程改进：** 审查涉及 SHA、回执、批准的代码时，逐个检查 `.or(...)`、`unwrap_or`、截断和默认值：兜底的结果是否仍满足 R1？不满足的话，就应该报错并转人工。每条不变量至少配一个反例测试。
- **反哺 Polyclave 设计：** 被审阅的、被推送的、传给 `enableAutoMerge(expectedHeadOid)` 的，必须是同一个经过 R1 核验的 SHA。评审输入不完整时（截断、只含部分提交），不允许给出 `approve`。

### 7. 交付记录和代码状态对不上
- **发生了什么：** 提交 `01c8645` 以"v5 验收后移除"为由删掉了 `legacy-node/`，但 `HANDOFF.md` 最后一条仍写着真实 CLI 和安装版 WebView 验收待完成，并要求保留 `legacy-node/`。同一时期，`README.md` 仍是 v4 的 Node 启动说明，`PRODUCT.md` 仍写"冻结"，`NEXT.md` 还指向已不存在的 Node 文件。外部审核者看到的是三套相互冲突的项目状态。
- **根因：** 删除、合并这类动作没有要求同时写下验收证据；入口文档不属于任何一个分支的工作清单，没人负责更新。
- **流程改进：** 删除旧实现或宣称"已验收"的提交，必须在 `HANDOFF.md` 里给出对应的验收条目：谁、哪次提交、在哪个平台跑了什么。每次合并之后，由合并审查者检查 `README.md`、`PRODUCT.md`、`NEXT.md` 是否还和代码一致。
- **反哺 Polyclave 设计：** 这正是 Polyclave 想替用户回答的问题："实际交付了什么，依据是什么"。项目自己的验收记录应该像 Run 回执一样，可以对应到具体的提交和证据。

### 8. 外部审核要先对齐它看的是哪个提交
- **发生了什么：** ChatGPT 的审核基于 `52bc69f`，之后又合进了 5 个提交。它说"默认 Reviewer 直接返回未启动"，这一点已经被 `6404845` 修了一半；"`dispatch_remote` 只能 ping 和搜索"也已经过时。逐条对照最新代码复核后，才发现真正的问题转移到了推送 ref 和返工 SHA 上。
- **根因：** 审核结论都绑定在某个快照上，代码一直在往前走。
- **流程改进：** 收到外部审核时，先记下它基于哪个提交，再到当前 `HEAD` 上逐条复核，标成"已修 / 仍成立 / 已过时"，然后才转给执行者。
- **反哺 Polyclave 设计：** Reviewer 的结论要绑定它审的 SHA。分支前进以后，旧批准不能沿用（R1 和 PR 门禁的 `expectedHeadOid` 就是这个用途）。

### 9. 外部 CLI 适配器必须以真实 `--help` / 实跑协议为准，不能用自造假脚本反向验证
- **发生了什么：** `dsh` 适配器传入了真实 `dsh headless` 并不存在的 `--model` 参数，且遗漏了 `mcp_url` 配置文件注入；由于单元测试用的是自己写的假脚本，所有测试全部通过，但真实运行必挂。
- **根因：** 适配器参数与事件解析器按文档推测编写，未针对本机真实二进制做参数白名单核对，也未在测试中检查 CLI 是否实际收到了 `mcp_url`。
- **流程改进：** 新增或修改任何 CLI 适配器时，必须先运行真实二进制的 `--help` 核对每一个 flag，并在适配器测试中强制断言 `mcp_url` 与一次性令牌均已通过该 CLI 支持的机制注入。
- **反哺 Polyclave 设计：** 守护进程启动或首次启用某厂商 Worker 前，可做一次只读 `--help` / 能力探测（probe），不兼容时提前 fail-closed 报错而非等到派活时静默失败。

### 10. 外部不可信事件严禁复用“本人显式指令”的入队通道
- **发生了什么：** `ScmObserver` 直接调用 `hub_enqueue` 把外部 GitHub 评论写成了 `source='user'`，绕过了 `Triage::inferred` 与机器人过滤；配对接口 `exchange_pairing` 也接受了请求体自报的 `peer_identity`。
- **根因：** 复用已有的便捷函数（`hub_enqueue`）或加便捷兜底（`header.or(body)`），没有按信任边界区分“本人显式输入”与“外部不可信数据”。
- **流程改进：** 审查所有跨信任边界的入口（Webhook/Observer、远端 HTTP、MCP 工具、Mesh 派发）时，强制核查数据落库时的 `source` / `actor` 字段是否来自可信宿主判定，禁止外部数据写入 `source='user'`。
- **反哺 Polyclave 设计：** 在存储层类型与 SQLite `CHECK` 约束上把 `hub_enqueue_user`（仅本地/已鉴权本人客户端可调）与 `hub_enqueue_external_event`（强制 `source='host'` 且必经 `Admission Policy`）物理拆开，从编译期堵死误用。

## 2026-11-27 · Batch 1 审查漏检复盘

### 11. 审查不能只看中间层与自检绿灯，必须从最外层入口追到底并对 OS/并发做故障模型审查
- **发生了什么：** 审查 `fix/hardening-batch1-runtime`（含自检提交 `2fdf2d6`）时，185 个测试全绿且代码整洁，初次审查给出通过结论；二次对抗复核在同一提交上发现两处实锤缺陷，且均出在自检新增代码里：① `POST /cancel` 只置内存标记，SQLite 中的 `mcp_revoked=1` 要等 Worker 退出回收后才落库，导致取消窗口内宿主 `commit_and_stage` 仍可继续写入 staging；② Windows `CommandTree::spawn` 采用 `CREATE_SUSPENDED` + `AssignProcessToJobObject` 两步绑定，两步间宿主崩溃会遗留挂起进程，且 `Drop` 只 `wait()` 主进程未确认孙进程树（如 `git-receive-pack`）已退出。
- **根因：** ① 只看了中间层回调（`can_publish`）与直接伪造数据库撤销状态的单元测试，未从最外层 HTTP 入口（`routes.rs` → `runner.rs` → `runs.rs`）逐跳追踪取消生效的真实时序；② 对 `windows.rs` 仅做了编译/Clippy 级静态检查，未做崩溃窗口与进程树排空的故障模型推演；③ 对“作者已自检 + 测试全绿”产生确认偏误，反而放松了对自检新增代码的对抗审查。
- **流程改进：** 合并审查强制执行三条硬检查：① 凡涉及取消、撤销、权限拦截，必须从最外层 HTTP/CLI 入口追到最底层落盘点，画出状态变更时序；② 凡改动 `polyclave-os`、锁、子进程或异步取消，强制追问三题（两步操作间宿主崩溃会遗留什么、孙进程树是否确认全退、取消/超时是否立刻对持锁方可见）；③ 对作者“自检补丁”新增的代码按最高风险面单独对抗审查。
- **反哺 Polyclave 设计：** 取消语义必须明确区分“已收到取消请求”与“已停止写入”，受理取消时立即撤销当前 turn 的写入与 MCP 权限（不可延迟到子进程回收后）；进程树托管应在创建进程时原子绑定隔离边界（如 Windows `PROC_THREAD_ATTRIBUTE_JOB_LIST`），并在清理阶段确认整棵进程树退出归零。
