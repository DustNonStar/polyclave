## 2026-11-26 · 多 Agent 协作与 v5 架构启动

### 1. 「遇冲突即停 + 结构化 A/B 选项与推荐」是最省返工的协作协议
- **发生了什么：** Dot 在 `dot/v5-phase1a` 动工前及 Task 4 前，先后通过 `PLAN-ISSUES.md` 拦下 3 处冲突：`authorized → go` 之间崩溃与已运行后退出的区分、`rusqlite` 无独立 `fts5` feature、v4 旧测试（取消冻结/复用旧 worktree）与 v5 Attempt 隔离的冲突，并给出带推荐项的 A/B 选项。
- **根因：** 实施计划在跨大版本迁移时未预先列出“旧测试语义变更白名单”，且部分底层边界（如 `authorized → go` 窗口）只有在真正写代码/跑校验时才会暴露。
- **流程改进：** 后续编写跨版本实施计划时，显式附上「旧测试语义变更白名单」；执行 Agent 遇到计划未授权的冲突时继续坚持“停下 → 写证据 → 给 A/B 选项与推荐”。
- **反哺 Polyclave 设计：** 阶段 1B 可为 Worker 新增结构化 MCP 工具 `raise_plan_issue({ level: 'detail' | 'direction', evidence, options, recommendation })`，`detail` 级由主控 `hub` 自动裁决放行，`direction` 级才弹窗请用户拍板。

### 2. 设计稿、规范文字与无头渲染预览的三方漂移
- **发生了什么：** 核查 `polyclave-v5-desktop-ui.fig` 时发现：底层线性渐变漏设垂直方向矩阵导致全局底部极光出现水平切线；`Deepy` 像素蓝鲸本身无脚，但规范文字笼统写成了“4 细腿”；Node 无头 CanvasKit 渲染因未注册系统 CJK 字体而隐藏了中文节点。
- **根因：** 视觉稿、设计文档和无头截图工具各自独立演进，缺少一步交叉核对。
- **流程改进：** 每次修改设计稿或规范后执行“图层 ↔ 规范文字 ↔ 实施计划”三方交叉核对；涉及中文字体视觉验收时，直接用原生桌面工具（OpenPencil）目视终审，不以无头截图作为唯一依据。
- **反哺 Polyclave 设计：** 阶段 1B 的无头浏览器验收门禁必须实测中文字体渲染与全局视口连续性，不能仅靠 DOM 断言。

### 3. 多 Agent 并行推进时的「零冲突分支纪律」
- **发生了什么：** Dot 在 `dot/v5-phase1a` 上实施阶段 1A 底座期间，我们在本地 `main` 补充了阶段 3（`google/agentmesh`）、阶段 4（社区工作流蒸馏）设计及经验库，但刻意不触碰 1A 计划文件且暂缓推送 `main`。
- **根因：** 若在执行 Agent 拉出工作分支后频繁往 `main` 推送或改动其正在执行的计划文件，会制造无谓的 rebase/merge 冲突。
- **流程改进：** 分支执行期间，`main` 只做不重叠的远期文档演进并暂留本地；待分支审查合并后再统一合流推送。
- **反哺 Polyclave 设计：** 主控 `hub` 同时调度多个 Worker 时，对同一仓库的共享契约/文档变更应串行化或在独立整合窗口合流。

### 4. 「云端确定性闭环 + 本机实机门禁」的分层验证
- **发生了什么：** Dot 在云端 Linux 环境跑通了确定性离线测试与 macOS/Windows 交叉编译及 Clippy，同时明确标注真实双平台运行与 `POLYCLAVE_REAL_CODEX/CLAUDE` 探针需留待本机合并审查时实跑。
- **根因：** 云端分支执行环境缺乏用户本机真实 CLI 登录态与双平台真机环境，硬凑反而容易引入虚假 mock 或泄露凭据。
- **流程改进：** 明确分层验收边界：分支执行 Agent 负责确定性离线闭环与 CI 编译/静态检查；合并审查者负责本机双平台实跑、真实 CLI 探针与 UI 实测。
- **反哺 Polyclave 设计：** 与 Polyclave “Worker 在 `network_access=false` 沙箱跑确定性闭环，宿主在可信本机执行 R1 核证与最终门禁”的架构完全一致。

## 2026-11-27 · `main@3dec8e4` 全项目审查

### 5. 测试全绿，但测试夹具自己伪造了生产环境里不存在的前提
- **发生了什么：** PR 门禁（`pr_gate.rs`）推送的是 `refs/polyclave/runs/<runId>/final`。生产代码里没有任何地方创建这个 ref，R1 验收写的是 `refs/heads/polyclave/<runId>`。只有测试 `hub_api/tests.rs` 手工推了 `final`，所以离线测试、macOS 和 Windows CI 全部通过，真实运行时第一次推送就会失败。
- **根因：** 端到端测试的前置状态由测试自己手工搭出来，没有走生产代码的产出路径。两个模块之间的约定（ref 名）因此只在测试里成立。
- **流程改进：** 凡是跨模块交接的前置状态（ref、表记录、文件），测试都要调用生产函数来产生，不能手写。审查时专门搜一遍：测试里出现的字面量 ref、路径或键名，生产代码里有没有对应的写入方。
- **反哺 Polyclave 设计：** 门禁推送的应该是已核验的确切 SHA（`<sha>:refs/heads/<branch>`），推送后再核对远端分支顶端，而不是推送一个"应该指向它"的 ref 名。

### 6. 兜底分支悄悄绕过了核心不变量
- **发生了什么：** 返工执行器返回 `run.result_sha.or(run.observed_sha)`。R1 没有接受结果时，它退回到"观察到的 SHA"，于是未经核验的提交可能被送去评审，甚至被批准。同一批代码里，Reviewer 用的是 `git show <head>`，只看到最后一个提交；diff 超过 24 KB 被截断时，模型也不知道。
- **根因：** 为了"总能拿到一个 SHA"或"别让提示词太长"而写的兜底，没有对照 R1 去检查。测试只覆盖正常路径，从没构造过只有 `observed_sha` 或多提交的情况。
- **流程改进：** 审查涉及 SHA、回执、批准的代码时，逐个检查 `.or(...)`、`unwrap_or`、截断和默认值：兜底的结果是否仍满足 R1？不满足的话，就应该报错并转人工。每条不变量至少配一个反例测试。
- **反哺 Polyclave 设计：** 被审阅的、被推送的、传给 `enableAutoMerge(expectedHeadOid)` 的，必须是同一个经过 R1 核验的 SHA。评审输入不完整时（截断、只含部分提交），不允许给出 `approve`。

### 7. 交付记录和代码状态对不上
- **发生了什么：** 提交 `01c8645` 以"v5 验收后移除"为由删掉了 `legacy-node/`，但 `HANDOFF.md` 最后一条仍写着真实 CLI 和安装版 WebView 验收待完成，并要求保留 `legacy-node/`。同一时期，`README.md` 仍是 v4 的 Node 启动说明，`PRODUCT.md` 仍写"冻结"，`NEXT.md` 还指向已不存在的 Node 文件。外部审核者看到的是三套相互冲突的项目状态。
- **根因：** 删除、合并这类动作没有要求同时写下验收证据；入口文档不属于任何一个分支的工作清单，没人负责更新。
- **流程改进：** 删除旧实现或宣称"已验收"的提交，必须在 `HANDOFF.md` 里给出对应的验收条目：谁、哪次提交、在哪个平台跑了什么。每次合并之后，由合并审查者检查 `README.md`、`PRODUCT.md`、`NEXT.md` 是否还和代码一致。
- **反哺 Polyclave 设计：** 这正是 Polyclave 想替用户回答的问题："实际交付了什么，依据是什么"。项目自己的验收记录应该像 Run 回执一样，可以对应到具体的提交和证据。

### 8. 外部审核要先对齐它看的是哪个提交
- **发生了什么：** ChatGPT 的审核基于 `52bc69f`，之后又合进了 5 个提交。它说"默认 Reviewer 直接返回未启动"，这一点已经被 `6404845` 修了一半；"`dispatch_remote` 只能 ping 和搜索"也已经过时。逐条对照最新代码复核后，才发现真正的问题转移到了推送 ref 和返工 SHA 上。
- **根因：** 审核结论都绑定在某个快照上，代码一直在往前走。
- **流程改进：** 收到外部审核时，先记下它基于哪个提交，再到当前 `HEAD` 上逐条复核，标成"已修 / 仍成立 / 已过时"，然后才转给执行者。
- **反哺 Polyclave 设计：** Reviewer 的结论要绑定它审的 SHA。分支前进以后，旧批准不能沿用（R1 和 PR 门禁的 `expectedHeadOid` 就是这个用途）。

### 9. 外部 CLI 适配器必须以真实 `--help` / 实跑协议为准，不能用自造假脚本反向验证
- **发生了什么：** `dsh` 适配器传入了真实 `dsh headless` 并不存在的 `--model` 参数，且遗漏了 `mcp_url` 配置文件注入；由于单元测试用的是自己写的假脚本，所有测试全部通过，但真实运行必挂。
- **根因：** 适配器参数与事件解析器按文档推测编写，未针对本机真实二进制做参数白名单核对，也未在测试中检查 CLI 是否实际收到了 `mcp_url`。
- **流程改进：** 新增或修改任何 CLI 适配器时，必须先运行真实二进制的 `--help` 核对每一个 flag，并在适配器测试中强制断言 `mcp_url` 与一次性令牌均已通过该 CLI 支持的机制注入。
- **反哺 Polyclave 设计：** 守护进程启动或首次启用某厂商 Worker 前，可做一次只读 `--help` / 能力探测（probe），不兼容时提前 fail-closed 报错而非等到派活时静默失败。

### 10. 外部不可信事件严禁复用“本人显式指令”的入队通道
- **发生了什么：** `ScmObserver` 直接调用 `hub_enqueue` 把外部 GitHub 评论写成了 `source='user'`，绕过了 `Triage::inferred` 与机器人过滤；配对接口 `exchange_pairing` 也接受了请求体自报的 `peer_identity`。
- **根因：** 复用已有的便捷函数（`hub_enqueue`）或加便捷兜底（`header.or(body)`），没有按信任边界区分“本人显式输入”与“外部不可信数据”。
- **流程改进：** 审查所有跨信任边界的入口（Webhook/Observer、远端 HTTP、MCP 工具、Mesh 派发）时，强制核查数据落库时的 `source` / `actor` 字段是否来自可信宿主判定，禁止外部数据写入 `source='user'`。
- **反哺 Polyclave 设计：** 在存储层类型与 SQLite `CHECK` 约束上把 `hub_enqueue_user`（仅本地/已鉴权本人客户端可调）与 `hub_enqueue_external_event`（强制 `source='host'` 且必经 `Admission Policy`）物理拆开，从编译期堵死误用。

## 2026-11-27 · Batch 1 多 Agent 审查协作复盘

### 11. 警惕上游 Agent“自检通过”带来的信任锚定效应，审查 Agent 严禁因对方自查而降低深度
- **发生了什么：** 执行 Agent（Codex）在提交 `fix/hardening-batch1-runtime` 时主动附带了自检修复提交、工整的交接报告和 185 个全绿测试。下游审查 Agent（Gemini）看到“对方已自检 + 测试全绿”后，没有做全链路深读，只跑了基础检查并抽看了局部代码就给出了通过结论；结果由另一轮独立深度复核在同一提交中查出两处实锤阻断，且两处都恰恰出在那个“自检提交”的新增代码里。
- **根因：** 多 Agent 串行协作中的**确认偏误与责任稀释**——当上游 Agent 表现出高完成度、主动自检并给出清晰总结时，下游审查 Agent 会下意识切换为“核对对方有没有做到它宣称的点”的浅层验证模式，把对方的自检报告当成可信背书，从而跳过了跨文件端到端链路追踪与对抗性深读。
- **流程改进：** 审查 Agent 接手任何分支时，必须把上游 Agent 的自检结论、通过声明和测试数字视为**不可信输入**，不得因此缩减代码阅读范围或跳过关键路径；越是“自检补丁”或“返工补丁”，越容易在仓促收口时引入新盲区，必须按全量独立盲审标准逐行审查。
- **反哺 Polyclave 设计：** Polyclave 的异构 Reviewer 与多 Agent 编排机制不应把 Worker 的“我已自查 / 测试全绿”话术作为降低评审深度的依据；传给 Reviewer 的上下文应与 Worker 的自我背书隔离，只提供客观产物（精确 SHA 的完整 diff、宿主核证事实），并对返工提交执行与初稿同等严格的独立评审。

### 12. 遇阻上报必须带“设计盲区归因 + 多选项取舍 + 项目目标对齐”，不能只甩报错或单一修法
- **发生了什么：** 多轮协作中，只有当执行或审查 Agent 把冲突写成“问题与证据 → 为什么会出现（是否暴露设计前提盲区）→ 2–3 个选项的含义/优缺点/取舍 → 结合项目当前目标的推荐方案与理由”（如 Mesh 预算 A+C、按 SHA 记录测试结果、外部消息隔离），人类决策者才能一轮拍板、不走弯路；只扔报错或只给单一修法往往导致来回追问甚至局部打补丁掩盖架构缺口。
- **根因：** 执行 Agent 天然聚焦手头局部任务，容易忽略跨模块约束与产品主线目标；缺少结构化四段式上报协议时，信息翻译成本全压在人类中枢身上。
- **流程改进：** 固化 `AGENTS.md` 中的四段式 `PLAN-ISSUES.md` 上报规范，并区分 `detail`（中枢裁决）与 `direction`（必须四段式呈递用户拍板）；每次上报必须显式追问“是不是原设计前提有未考虑到的地方”。
- **反哺 Polyclave 设计：** 将该四段式结构直接固化为 Hub 的 `raise_plan_issue` 协议与 `direction` 决策卡片模板，让用户永远看到“是什么、为什么、有哪些取舍、为什么推荐这一项”。

### 13. “干活自检”与“异构盲审”必须职责分层、信息隔离，返工超限要熔断回设计层
- **发生了什么：** 实践证明，“中枢定方向与权衡 → 执行 Agent 干活并自检 → 异构模型独立盲审 → 用户看客观证据拍板”是最稳的四段式协作流；但若不限制返工轮次，局部修补会在错误的设计前提上越叠越厚。
- **根因：** 自检与盲审承担不同职责——自检清理低级回归、盲审打破单一模型思维盲区；两者既不能互相替代，也不能在设计假设本身有误时无限循环打补丁。
- **流程改进：** 明确“执行自检（须诚实标注离线假件与真实环境边界）→ 异构盲审（隔离自检背书）”两段交接；并在 `REVIEWER.md` 增加 **2 轮返工熔断规则**——同一问题返工 2 轮仍未过审，立即停工回到设计层重审前提并向用户呈报选项。
- **反哺 Polyclave 设计：** 在 `pr_gate` 与 `TurnRunner` 中落实返工轮次熔断（达到上限自动停手并升级回 Hub 做设计前提复盘，而不是继续调度 Worker 盲目返工），同时在审批卡上始终严格分离“Worker 自报”与“宿主/CI 客观核证”。

## 2026-11-28 · `main@0b593c7` 真机验收前四模型独立盲审复盘

### 14. 任何单次审查都是抽样而非全覆盖：可判定不变量 + 异构独立盲审 + 源码裁决 + 真机兜底
- **发生了什么：** 在 `main@0b593c7` 本地 209+ 项测试、浏览器测试与 macOS/Windows 双平台 CI 全绿、准备进入单故事真机验收前，我们按统一范围提示词（聚焦真机 5 条接缝 + 暂停模块高危安全阀）对 4 个不同模型（Claude Opus 5.5、DeepSeek Harness、Gemini 4、GPT-6）开启全新独立会话发起只读盲审，再由主控 Agent 逐条回到同一 commit 源码按图索骥复核。结果显示：**4 份报告中的所有正向 P0（去重后 10 项）与 2 项安全阀漏洞经源码核实均真实存在**（个别条目存在定级分歧，例如 `tauri.conf.json` 当前 `bundle.active=false` 下 Finder `PATH` 属打包前必修而非本次终端验收硬阻断；Codex 同 UID 可读 `state_dir` 属已知沙箱边界），同时呈现出极强的交集印证与差集互补（10 项 P0 中整整一半仅由单一模型独有发现）：
  - **多模型交叉印证的共性阻断：** GitHub `CLEAN` 状态 PR 调 `enablePullRequestAutoMerge` 失败后 Gate 永久卡死在 `approved`（Claude / Gemini / GPT-6）；武装状态下重跑 Gate 建兄弟行可向同一 PR 推入未批准 SHA（Claude / GPT-6）；返工 Attempt B 的 `commit_and_stage` 无视 `attempts.from_sha` 回退到 `base_sha`，局部 `paths` 提交会静默抹除 Attempt A 改动（Gemini / GPT-6）；Claude Seatbelt 沙箱认证死路与凭据读/外传边界（Claude / Gemini / GPT-6）；前端无首次建 PR Gate 入口与默认 Reviewer 死路（DeepSeek / Gemini / Claude / GPT-6）。
  - **各模型独有的关键发现（其余 3 个模型均未捕获）：**
    - **Claude Opus 5.5：** 用本机 `/usr/bin/sandbox-exec` 探针实证缺少 `/private/var/run/mDNSResponder` 导致沙箱内 DNS 解析必挂；发现 `Ctrl-C`/`SIGTERM` 优雅关停后 Worker 活过已关闭的 MCP 并与新 daemon 交叉踩库；发现 `run_pr_gate` 同步阻塞在 MCP `tools/call` 必然被超时掐断。
    - **DeepSeek Harness：** 发现从 Finder/Spotlight 启动 Tauri 桌面壳时伴生 `polyclaved` 继承最小 `PATH` 导致找不到 Homebrew/nvm 下的 `codex`/`claude`；发现启动期失败被静默写进前端未读的 `Inbox` warning 并误报为 `retryable`。
    - **Gemini 4：** 发现 Codex CLI Hub 漏配 `default_tools_approval_mode="approve"` 且 Claude CLI Hub `CENTRAL_TOOLS` 漏配 `run_pr_gate`；发现手机端审批卡缺少同 SHA 测试与未决项，且 `awaiting_human_approval` 在 `Needs you` 与唤醒通知中隐身；触发安全阀查出技能同步沿 symlink 写穿用户全局目录与社区草稿脱敏分词绕过。
    - **GPT-6 (Codex)：** 发现桌面端撤销已配对手机后，存量 SSE 长连接仍可持续收到新增 Hub 消息与实时输出；发现 `diffPanel` 静默截断 400 行以外尾部；发现同 SHA 重跑 check-runs 产生新 ID 时旧失败行残留 SQLite 导致 UI 永远标红。
  - **对“覆盖率假阴性”的反向教训：** 4 个模型复盘时坦承，即便逐行读过同一段代码（如 `stage.rs`、`evolution.rs`、`claude.rs`），仍会因切入问题不同而漏掉其他模型的 P0；并且报告中未深查区域写“无”属于高风险覆盖率主张（例如安全阀项被写成“无”但实际存在漏洞）。
- **根因：** 一方面，单模型自写代码、自写 mock 测试与自检会形成假设同源的局部自洽闭环；另一方面，**注意力的分配由带入代码的问题决定，与是不是作者无关**——任何单次审查（人或模型）都只是一次抽样而非全覆盖，且静态审查天然存在“外部真实环境黑盒”的天花板。
- **流程改进：**
  1. 在重大里程碑（真机验收、发版、核心安全边界变更）前，固化四步门禁：**先写清可判定的不变量 → 独立新会话 + 强证据约束并行盲审（按高风险接缝/异构模型组合，禁止对未查区域写“无”）→ 回到同一 commit 源码逐条裁决并校准定级 → 真机验收兜底环境黑盒**；日常小改动保持“1 Worker + 1 异构 Reviewer”控制成本。
  2. 遇到多条同类缺陷时先立架构不变量再写补丁（本次沉淀 4 条核心不变量：**I1** 同 Run 至多一个活 Gate 且武装后 SHA 不可变；**I2** 返工提交必从持久化 `from_sha` 建索引；**I3** PR Gate 长流程必为宿主后台作业；**I4** 撤销设备必立即切断全部存量 SSE 连接）。
- **反哺 Polyclave 设计（对外推广核心案例）：** 这次实战直接印证了 Polyclave 的核心方法论——不是“简单堆多模型”，而是**“可判定不变量 + 异构独立盲审（扩 recall）+ 宿主客观核证与源码裁决（守 precision）+ 真机/人类最终把关”**。对外推广时可直接用 `main@0b593c7` 的三个真实标本讲清价值：①“测试全绿但真机必挂”（Seatbelt DNS / 返工 `from_sha`）；②“同一行代码、不同模型问出不同 P0”（`allow file-read*` 能否运行 vs 能否外传凭据）；③“已有测试只保新请求，盲审抓出存量连接”（撤销设备后 SSE 仍推消息）。

### 15. 异构审查的“三级成本阶梯”与按角色预设“模型 + 推理等级”
- **发生了什么：** 在 `main@0b593c7` 真机验收前，我们跑了一次“满配多轮交叉盲审”：四家分别选用代表性主力模型与高/极高推理预算（Codex 6.2 sol max、Claude Opus 5.5 超高思考强度、DeepSeek v4.1 flash max、Gemini Neon 极高推理）独立盲审，主控汇总验真后又把汇总发回各模型做第二轮交叉纠偏。效果极好（不仅挖出 10 项 P0 与 2 项安全阀，还在第二轮纠偏出汇总本身的定级分歧与 4 条架构不变量），但 Token 与墙钟耗时都很可观；同时每次切换角色或发起盲审都需要人工在会话里重复指定模型与思考强度。
- **根因：** 不同研发节点的风险密度差异极大——如果只有“单模型自检”和“四模型多轮互评”两个极端，要么质量漏网、要么成本失控；而缺少角色级默认配置时，每次派工或盲审都要靠人手动挑模型与推理档位，增加心智负担且容易选错。
- **流程改进：** 将异构审查固化为**三级成本阶梯**，按风险密度按需选用：
  1. **日常级（1 Worker + 1 异构 Reviewer）**：常规单次迭代与小步提交，控制成本的同时打破单一模型同源盲区。
  2. **省 Token 盲审级（多模型单轮独立盲审 → 单一主控汇总验真）**：重要功能合入或常规阶段验收前使用——各厂商主力模型只跑一轮独立盲审，完成后仅由一个主控模型按图索骥回源码核实与定级裁决，不再把汇总发回各模型做第二轮互评讨论，大幅节省 Token。
  3. **里程碑满配级（多模型独立盲审 → 主控汇总 → 各模型二次交叉互评与纠偏）**：仅在重大里程碑、真机端到端验收前、或核心安全/架构方向拍板时启用，换取最高维度的覆盖率与定级校准。
- **反哺 Polyclave 设计：** 在 Polyclave 的 Settings / Agent 配置中，支持为不同 Agent 与角色（Hub、Worker、Reviewer、Council/盲审席位）**预先绑定具体的模型 ID 与推理等级（reasoning effort / thinking budget）**，并提供上述三档审查模式预设；派发任务或触发盲审时自动沿用预设，无需在每次会话或任务下发时重复手动指定。
