# Polyclave 设计 v4：自建宿主 + 手机 App

- 项目名：**Polyclave**（2026-11-25 定名；原称"Agent 控制台"，曾短暂定名 Conclave）。本仓库从一个更早的私有原型拆出，只含本项目的方案、计划和实测记录。文中提到的 11-20 版设计、v3.1（T3 结合方案）和 v5.3（dev 流程）都是未公开的早期设计；本文沿用它们的内容已写在正文里。

- 日期：2026-11-25
- 状态：draft v4，未经评审。
- 取代：早期的 T3 结合方案（draft v3.1，未公开）的整体架构。v3.1 的派活规则、偏好与范围、dev 门禁、进化循环在本文中保留并改写到自建宿主上；T3 不再是依赖。
- 沿用：11-20 版设计（未公开）的目标（§1–§2）、角色（§6）、方案讨论规则（§8）、进化护栏（§9）。
- 依据：三轮实测（`docs/superpowers/research/2026-11-24-t3-probe-results.md`，第三轮是本文的直接依据）；信任模型（v3 §3.3，本文 §3）。

### 为什么从 v3.1 改到 v4

1. **用户不希望整个项目建立在 T3 Code 上。**
2. **第三轮实测证明可以不经 T3 直接调用各家 agent**：Claude、Codex、Antigravity 用各自的官方命令行各调一次，都按同一个 JSON schema 返回了结论；DSH 只差 `DEEPSEEK_API_KEY`。
3. T3 能提供的手机访问、推送、看线程，用 Tailscale + 自己的 App 就能做到，而且数据不经过 T3 的云。
4. T3 实测里学到的东西（reviewer 不能靠模式只读、结构化结果要有纠正和失败出口、流程重启不能重放副作用）照样适用，已写进本文。

## 1. 一句话

在你的 Mac 上跑一个**宿主服务**（我们自己写）。它直接启动和驱动各家官方 agent 命令行（Claude Code、Codex、Antigravity、DSH），运行流程（方案讨论、开发、评审、合并），把所有会话存在本地。你通过**桌面网页**或**手机 App（iOS 和 Android）**和总主会话对话；手机通过 **Tailscale** 连回 Mac。

## 2. 用户确认过的决策

1. **不以 T3 Code 为底座**：会话、流程、界面都由宿主自己管。T3 可以继续装着自己用，和控制台无关。
2. **保留总主会话 + 流程**：总主会话负责自由对话；流程负责确定性的步骤（方案讨论、dev、进化）。
3. **审查通过即自动合并**，由代码核对 SHA、测试、模型不同，不需要你确认。先以影子模式运行，验证通过后再真的合并（§17）。
3a. **决策分两级**（2026-11-25）：
   - **方向级**：项目开始时的大方向和整体方案（例如本项目这样，你和多家模型一起讨论），由**你**决定。方案讨论流程（§10.3）此时只汇总，不替你选。
   - **细节级**：方向定下后，实现过程中的具体选择（库、写法、拆分方式、小范围取舍），由**决策会话**按你的偏好决定，只在升级条件触发时问你。
4. **一个 macOS 账户**，本机 agent 按 Claude Code 的标准信任（§3）。
5. **手机端 iOS 和 Android 都做**，用同一套界面代码包装成 App。
6. **远程连接用 Tailscale**：直连不通时走 Tailscale 的中转，全程端到端加密。
7. **保留 CUA**；**Agent HUD 只用来看额度**。
8. 测试只做到"证明调用可行"为止，不再对 T3 做更多实测。

## 3. 信任模型（与 v3 相同）

- 本机 agent 和你现在用的 Claude Code、Codex 一样可信：在你的账户下运行，能读你的文件，可以使用你的 GitHub 账号或专用账号。
- 安全措施只防**出错**：防止合并没人审过的代码、合并审过后又变了的代码、改动超出你的要求、把 issue 里别人的话当成你的指令。**不防**本机有人或 agent 故意伪造。
- 因此不做多用户隔离、不做消息防伪；但宿主仍然把"你发的消息"和"agent 发的消息"分开记录（§9），因为这能防住"agent 把别人的话误当成你的指令"这类出错。

|---|---|---|---|---|

| worker | dev 流程的实现者 | 长期 ACP 会话，在 PR 的 worktree 里 | 改代码、跑测试、用 bot 账号推送和开 PR、调用 `submit_result` | approve、合并 |

## 6. Agent 之间怎么沟通

### 6.1 原则：星形，宿主是唯一的中转站

- **agent 之间不直接通话**。任何 agent 想让另一个 agent 做事，都必须调用宿主的 MCP 工具；由宿主决定是否执行、启动哪个 agent、把结果交回谁。
- 三条通道：

| 方向 | 通道 | 内容 |
|---|---|---|
| 宿主 → agent | ACP（长期会话）或单次命令行 | 发任务、发你的消息、取消 |
| agent → 宿主 | 宿主的 MCP 工具 | 提交结果、申请派活、申请咨询、拿 CUA 锁 |
| agent → agent | **只能**经宿主中转：`consult`（一问一答）或 `request_dispatch`（启动流程） | 问题与答案、派活申请 |

- 这也是对"ACP 让 agent 互相调用"的回答：ACP 只是宿主驱动 agent 的协议；MCP 才是 agent 调用外部能力的协议。我们让 agent 通过 MCP 调用宿主，再由宿主调用别的 agent。

**优点**
- 所有跨 agent 的交互都留在宿主的记录里，界面上能看到谁在什么时候问了谁什么。
- 能统一加限制：咨询深度只有一层、次数上限、超时、费用上限；不会出现 A 叫 B、B 又叫 A 的循环。
- 被调用的 agent 拿到的是宿主整理过的输入，结果也由宿主按 schema 校验，不会把一家的格式问题传给另一家。
- 派活一律经过 `request_dispatch` 的检查（§9），不会出现"某个 agent 自己决定开工"。

**缺点**
- 多一跳：咨询要经过宿主，比 agent 直接调用慢一点（主要耗时仍然是模型本身）。
- 灵活性受限：agent 不能自由组成小组讨论；需要多方讨论时只能走方案讨论流程。
- 宿主是单点：宿主挂了，所有会话都停（§7.5 讲重启恢复）。

### 6.2 两种运行方式

| 方式 | 用在哪里 | 怎么跑 | 结构化结果 |
|---|---|---|---|
| **长期 ACP 会话** | 总主会话、manager、worker；你直接对话的任何会话 | 宿主启动 agent 的 ACP 进程（stdio，JSON-RPC），一个会话一个进程，可多轮、可流式显示、可取消、能收到权限请求 | agent 调用宿主 MCP 的 `submit_result`（§6.4） |
| **单次调用** | analyst、reviewer、决策会话、`consult` 被咨询方 | 每次启动一个命令行进程，跑完退出 | 各家原生 schema 参数（已实测）；DSH 用提示词 + 宿主校验 |

为什么分两种：
- 单次调用简单、无状态，第三轮已经实测通过；评审和咨询本来就是一问一答，不需要保持会话。
- 需要多轮对话、你会中途插话、要看过程的角色，用 ACP 才能流式显示和随时取消。

### 6.3 宿主 MCP 工具

宿主为每个会话签发一个只属于它的令牌，MCP 服务按令牌判断会话的角色和所属流程运行，只给出该角色的工具。

| 工具 | 谁能用 | 做什么 |
|---|---|---|
| `submit_result({...})` | worker 等长期会话里需要返回结构化结果的步骤 | 宿主按该步骤的 schema 校验；不合格立即返回错误原因，让 agent 重交 |
| `request_dispatch({kind, level, project, payload, basis, then})` | 总主会话 | 申请启动流程（§9）；`level` 只用于 `council`，取 `direction` 或 `detail`，缺省按 `direction` |
| `consult({vendor, model?, question, context_paths?})` | 总主会话、manager、worker | 向另一家咨询一次（§6.6） |
| `run_status({runId})` / `run_list()` | 总主会话 | 读流程状态 |
| `cua_acquire()` / `cua_release()` | reviewer | CUA 锁（§11） |
| `report_progress({text})` | worker | 在界面上显示进度，不影响流程 |

agent 拿不到的：发"用户消息"的工具、回答流程提问的工具、提交 review 和合并的工具、改偏好和暂停开关的工具。这些只有客户端（你）或流程代码能用。

### 6.4 结构化结果（借鉴 T3 实测）

- 长期会话的步骤：宿主在任务说明末尾写明"完成后调用 `submit_result`，格式如下"。
  1. agent 调用 `submit_result`：宿主校验，通过则步骤完成。
  2. agent 结束 turn 却没交、或交的不合格：宿主发一条纠正消息，最多两次。
  3. 两次后仍没有合格结果：步骤失败，流程按失败分支处理（重试、换模型或问你）。T3 实测里这个"两次后放弃"的设计工作正常，我们照搬。
- 单次调用：用各家的 schema 参数（§6.5 表）；命令行返回后宿主再校验一次；不合格同样最多重跑两次。

### 6.6 `consult`：agent 之间的一问一答

1. 调用方（例如总主会话）调用 `consult({vendor: "openai", question, context_paths})`。
2. 宿主检查：调用方的角色允许咨询；本次流程运行的咨询次数未超上限（默认 5）；被咨询的厂商已启用。
3. 宿主用单次调用的方式启动被咨询方：只读（Codex `read-only` 沙箱；其他家在一次性 worktree 里），只附上 `context_paths` 指定的文件，超时默认 5 分钟。
4. **被咨询方没有 `consult` 和 `request_dispatch` 工具**，所以深度只有一层，不可能形成链条或循环。
5. 回答原样返回给调用方，并标明"来自 <厂商/模型> 的回答，不是用户指令"；同时在界面上显示为一条可展开的咨询记录。

**优点**：能用别家模型补盲点（第二意见、查资料、读一段陌生代码），且全程可见、有上限。
**缺点**：每次咨询都是一次新调用，没有上下文积累；需要上下文时要由调用方把相关文件路径列出来。

### 6.8 已实测：宿主接管一个 Codex 会话（2026-11-25）

脚本：`docs/superpowers/research/probes/codex-host-loop.mjs`（约 200 行，无第三方依赖）。宿主每次运行都是一个新进程，会话 id、MCP 令牌、消息、事件、结果都存在 SQLite。

| 步骤 | 结果 |
|---|---|
| 第 1 轮：新开会话，让它记住一个暗号 | 通过；从 `thread.started` 事件拿到会话 id，写入 SQLite |
| 第 2 轮：**新的宿主进程**用 `codex exec resume <id>` 续接，让它调用 `submit_result` | 续接成功（它记得暗号）；但工具调用被 Codex 拦下：`MCP tool call requires approval, but approval policy is never`。另外它还调用了你全局配置里的 hindsight MCP |
| 修正 | 加 `-c mcp_servers.host.default_tools_approval_mode="approve"`（只对宿主的工具免批准）和 `--ignore-user-config`（不加载你的全局 Codex 配置，只用宿主给的 MCP；登录不受影响） |
| 第 3 轮：再续接，调用 `submit_result` | **通过**：宿主校验通过，结果写入 SQLite 的 `results` 表 |
| 第 4 轮：故意先交不合格的结果 | 宿主拒收并返回原因；Codex 读到错误后改正重交，第二次通过。两次都记录在 SQLite |
| 第 5 轮进行中用 `kill -9` 杀掉宿主 | Codex 子进程**没有跟着退出**，继续跑完这一轮，它对宿主的 MCP 调用落空；SQLite 里只有你的消息，没有回复 |
| 第 6 轮：新宿主续接 | 续接正常，`submit_result` 写入成功 |

每轮 7～15 秒。

得出的设计要求（已写入 §7.5）：
1. **用户全局配置要隔离**：Codex 用 `--ignore-user-config`，Claude 用 `--strict-mcp-config`，否则 agent 会带上你自己的 MCP 和设置。
2. **只给宿主工具免批准**：不要整体放开批准策略。
3. **宿主要管住子进程**：子进程放进单独的进程组，宿主退出时一起结束；宿主启动时根据 SQLite 里记下的 pid 清理上次留下的子进程，确认没有残留后再续接同一个会话，避免两个进程同时写同一个会话。
4. **每轮一个进程 + `exec resume`** 对 Codex 已经够用：事件是 JSONL 流，能实时显示；会话存在 Codex 自己的记录里，宿主只需记 id。ACP 只在需要中途接收权限请求时才有额外价值，Codex 可以先不用 ACP。
5. 中断的那一轮在 SQLite 里没有回复。宿主要在启动时把这类轮次标为"中断"，并在下一条消息前告诉 agent"上一轮被中断"。

### 6.7 一条消息走完全程的例子

你在手机上说："给 my-app 加导出 PDF 功能，做完直接合并。"

1. **手机 App → 宿主**：App 通过 Tailscale 把消息发到 `POST /sessions/main/messages`，带设备令牌。宿主存为一条 `source = user`、`client = ios` 的消息，再通过 ACP 转给总主会话。
2. **总主会话**理解需求，调用 `request_dispatch({kind: "council", project: "my-app", payload: {...}, basis: <你这条消息的 id>, then: "dev"})`。
3. **宿主检查派活**（§9）：`basis` 是你发的、没用过、项目已登记 → 通过。宿主记下范围契约，在总主会话里贴出派活卡片，启动方案讨论流程。
4. **方案讨论流程**（§10.3）：并行让每家 manager 出一个 `Proposal`（互相看不到），宿主隐去厂商名，决策会话按你的偏好选一个；没触发升级条件，所以不问你。汇总贴回总主会话；手机收到一条"方案已选定"的推送。
5. **dev 流程**（§10）：analyst 出 `Plan` → worker 在 worktree 里实现，用 bot 账号推送、开 PR，调用 `submit_result` 交出 PR 号和 head SHA → 宿主做范围检查 → 两家 reviewer 在一次性 worktree 里评审这个 SHA，返回结论 → 宿主核对 SHA 后用 reviewer 账号 approve → 宿主开启 auto-merge，等 GitHub 实际合并后核对合入的 SHA。
6. **完成**：总主会话里出现结果卡片（PR、评审结论、合并的 SHA），手机收到推送。

途中如果 worker 想问 Codex 某个库怎么用，它调用 `consult`（§6.6）；如果出现升级条件（例如要改鉴权代码），流程的 `ask` 会推送到你手机，你在通知上或 App 里回答。

## 7. 会话管理

### 7.1 统一事件格式

各家适配器把自己的输出转成同一种事件，界面和流程只认这一种：

```ts
type AgentEvent =
  | { kind: 'message.delta'; text: string }
  | { kind: 'message.done'; text: string }
  | { kind: 'tool.call'; name: string; input: unknown }
  | { kind: 'tool.result'; name: string; ok: boolean }
  | { kind: 'permission.request'; id: string; what: string }
  | { kind: 'turn.done'; usage?: Usage }
  | { kind: 'error'; message: string }
```

### 7.2 一个会话的生命周期

1. **创建**：宿主按角色生成启动参数（模型、工作目录、MCP 令牌、权限、说明文字），启动子进程，记下 agent 自己的会话 id（用于续接）。
2. **发消息**：每个会话一个发送队列。一个 turn 进行中时，新消息排队，等 `turn.done` 后再发。你在界面上可以选择"插话"：先取消当前 turn，再发你的消息。
3. **权限请求**：ACP 的权限请求由宿主按角色策略自动回答——worker 在自己的 worktree 里自动批准；越界的拒绝并记录。不把权限请求推给你（T3 实测里"需要批准"模式会让 Codex 卡住）。
4. **取消**：ACP 的取消请求；单次调用直接结束进程。
5. **关闭**：常驻会话不关闭；流程里的会话在步骤结束后关闭，记录保留。

### 7.3 权限策略

- 真正的隔离靠各家自带的沙箱或权限模式（§6.5 表）。宿主的判断主要用于防误操作和审计。
- 不支持沙箱的 agent 在界面上标"无沙箱"。
- 进程环境：worker 的环境里只有 bot 账号的 GitHub 令牌；reviewer 和其他会话没有任何 GitHub 写权限令牌；reviewer 账号的令牌只在宿主进程里。

### 7.4 存储

- `polyclave.sqlite`：项目列表、会话、消息（含来源）、事件、流程运行和步骤记录、在途 PR 台账、偏好、运行记录。
- 每条消息记录 `source`（`user` / `agent` / `host`）、`client`（`desktop` / `ios` / `android`，仅 `user`）、`session`、`run`。

### 7.5 宿主重启

- 子进程管理（§6.8 实测：宿主被杀后 Codex 子进程会继续运行）：
  - 每个 agent 外面套一个**监护进程**：监护进程是独立进程组的组长，agent 在它的组里；它一旦发现宿主不在了（父进程变了），就结束整组。这样宿主崩溃后 agent 不会继续跑（借鉴 Orca，见 `docs/superpowers/research/2026-11-25-orca-comparison.md`）。
  - 进程组号和**进程启动时间**写入 SQLite。确认"还是不是原来那个进程"只看启动时间，不看命令行文字，避免 pid 被别的程序复用时误杀。
  - 存活状态分三种：存活、已退出、**无法确认**。无法确认时不杀进程、不自动重试，相关任务转人工核对。
  - 宿主启动时仍会按记录清理残留的进程组（监护进程本身被强杀时的兜底），确认没有旧进程后再续接会话，保证同一个会话同一时间只有一个进程。
  - 没有回复的轮次标为"中断"；续接后发的第一条消息先说明"上一轮被中断"。
  - 同一会话同时只能有一轮"进行中"：用数据库唯一约束保证，不用"先查再写"。
- 中断任务的处理（§17.1 实测）：**先对照外部状态，再决定**，不能只凭本地记录重试。
  - 外部没有这次任务的痕迹，也没有被接受的结果 → 可以重试（续接会话时告诉 agent 先检查本地已有的工作，复用而不是重做）。
  - 宿主已接受过结果，且外部状态和接受的结果完全一致 → 完成。
  - 其余情况（外部已有但没有被接受的结果、外部和接受的结果不一致）→ 保留外部状态，标为"需要人工核对"，推送给你，不自动重试。
  - **推送了不等于做完了**（2026-11-25 复审修订）：分支上的运行 id 只能证明是谁写的，不能证明做完了。崩溃恢复实测里能"直接采纳"，是因为那个任务的内容是固定的；正式任务不能这样判断。
- 任务进行期间占用会话：你发给这个会话的新消息排队，等任务完成、取消、失败或转人工核对后再处理，不会插进任务的两轮之间。
- agent 交的结果必须绑定任务 id 校验：被中断的 agent 在下一轮会去补报上一个任务的结果。
- 宿主工具的令牌**每一轮一个**：这一轮结束（完成、取消、中断）就失效，旧进程或子代理拿着旧令牌交来的东西直接被拒。同一任务交来完全相同的结果按幂等处理（回答"已接受"，不重复记录）。
- 每个任务最多手动重试 3 次，超过后转人工核对。
- **2026-11-25 复审修订（GPT，详见 `docs/superpowers/plans/2026-11-25-polyclave-phase1-gate-a-revisions.md`；用户选择"冻结、由你处理"）：**
  - **进程组空了不等于没有写入者。** Codex 在 macOS 上用新会话（setsid）运行命令（§20），宿主杀掉进程组后，已经启动的 `git` 命令仍可能写 worktree 或推送。所以：只要 agent 已经被允许运行，之后宿主崩溃（同一次开机内）或你取消了任务，就**冻结这个会话**，任务转"需要人工核对"；冻结期间这个会话不启动任何新的一轮（聊天、排队消息、纠正、重试都不行），直到你在界面上解冻。能排除写入者的只有两种情况：agent 从未被放行，或电脑已经重启过。
  - **宿主身份**：每次启动生成一个实例 id，按实例 id（不是 pid）判断哪些轮次属于已死的宿主。
  - **启动握手**：监护进程先报告就绪，宿主把这一轮、进程组号和启动时间写进数据库后才发出"放行"，监护进程收到放行才启动 agent。崩溃发生在放行之前，就能确定 agent 从未运行。
  - **受理幂等**：创建任务带客户端生成的请求 id，同一请求重发得到同一个任务；任务从受理起就占住会话（数据库约束），`pending` 的任务在恢复时也有去向。
  - **每个任务有自己的 worktree、分支和固定的起点提交**，有自己的 Codex 线程；agent 直接推到固定的裸库绝对路径。完成要求：被接受的结果等于远端分支最新提交，起点是它的祖先，中间至少一个提交，每个提交都有真正的 git trailer `Run-Id`。
  - **所有出口共用一张判定表**（正常结束、异常退出、取消、恢复、重试）；推送了但没交结果的，立即转人工核对，不再发纠正。
  - **结果提交无竞态**：远端检查做完后，在一个短事务里重新确认这一轮仍有效再写入；每个任务只能有一条被接受的结果。
  - **你的处理入口**：对"需要人工核对"的任务可以选择接受（以当时看到的提交为准）、判为失败或允许重试，都会记下你的说明和看到的提交；解冻会话也要写一句说明。
  - 界面上 `done` 显示为"交付已核对"：只证明交付到了哪个提交，需求是否满足由测试和阶段 2 的评审判断。
- **2026-11-25 第二次复审修订（Gemini，详见 `docs/superpowers/plans/2026-11-25-polyclave-phase1-gemini-review.md`）：**
  - **取消也冻结**：不论聊天还是任务，取消一个已放行的轮次都会冻结会话（你就在界面前，确认后点一次解冻即可）；冻结和结束这一轮写在同一个事务里，之后进程退出的回调不能再改写这一轮的状态。
  - **重试和纠正不会并行**：认领一轮时说明是首轮、纠正、重试还是聊天；纠正必须紧接在同一任务的上一轮之后，重试在同一事务里检查次数上限。
  - **你接受的是你看到的那个提交**：接受时要带上你看到的 SHA；如果远端已经变了，宿主拒绝并让你看新的提交。
  - **worktree 在每次开始和重试前都会准备**，复用已有目录前核对它属于这个仓库、在正确的分支、从起点提交派生。
  - **路径一律先取真实路径**：Codex 的 macOS 沙箱拒绝相对路径和含符号链接的路径（`/tmp`、`/var`）。提交说明必须有空行再接 `Run-Id` trailer，否则 git 不认为它是 trailer。
  - 开机时间只取秒数（不受时区影响），进程启动时间固定用英文和 UTC 读取；宿主锁用排他创建；裸库还要求 `receive.denyNonFastForwards=true`。
- 常驻会话：重启后用记下的会话 id 续接（各家的续接参数见 §6.5）；续接失败则新开，并把最近的对话摘要作为第一条消息。
- 进行中的流程：见 §8.3。

## 8. 流程引擎

### 8.1 写法

流程是 TypeScript 函数，用几个原语（参照 T3 workflow 的接口，它们的行为已实测过）：

| 原语 | 作用 |
|---|---|
| `step(name, fn)` | 一个代码步骤；完成后结果写入记录 |
| `agent(name, {role, vendor, model, brief, returns, workspace, timeout})` | 一个 agent 步骤，按 §6.2 选运行方式；`returns` 是 schema |
| `agent.try(...)` | 同上，但失败时返回 `{outcome: "failed", reason}` 而不是让流程失败 |
| `ask(name, {title, choices})` | 问你，推送到手机；等你回答 |
| `parallel([...], {concurrency})` | 并行 |
| `sleep` / `waitFor(signal)` | 等待 |

### 8.2 持久化

- 每个步骤开始和结束都写入 SQLite，带步骤名和输入的哈希。
- 流程从头重新执行函数时，已完成的步骤直接返回记录里的结果，不再执行（"重放"）。
- 有副作用的代码步骤（推送、开 PR、提交 review、合并）必须是可以重复执行而结果不变的：每个副作用带一个由运行 id、步骤名、**评审轮次和 head SHA** 派生的键（否则第二轮评审会命中第一轮的记录）；**先把操作意图写进 SQLite，再调用 GitHub**，恢复和暂停时核对所有未结算的意图，执行前先查 GitHub 上是否已经完成。
- agent 执行的外部动作（例如 worker 推送、开 PR）宿主**无法事前拦截**：agent 常把提交和推送写在同一条命令里（§17.1 实测）。所以这些动作必须留下能查回来的标识——分支名带运行 id（`agent/<run>`），PR 正文带 `[run:<id>]`——供重启后对照。

### 8.3 失败和重启

- 步骤失败：流程停在"失败"状态；你（或总主会话代你）选择"继续"时，只重跑失败的步骤（与 T3 实测行为一致）。
- 宿主在流程等待 `ask` 时重启：回答后接着往下走，已完成步骤不重放（与 T3 实测行为一致）。
- 宿主在 agent 步骤进行中重启：
  - 单次调用：重新启动这次调用（单次调用没有副作用，或副作用在一次性 worktree 里）；
  - 长期会话（worker）：**先按 §7.5 做恢复核对**（实例、写入者、远端），会话冻结时什么都不做；只有核对后允许重试，才续接原会话或在同一个 worktree 里新开会话。
- 同一个流程同一时间只有一个执行者（SQLite 里的运行锁）。

### 8.4 并发

- 全局 worker 上限和每个项目的上限。
- 同一个 manager 会话同一时间只参加一次方案讨论，后到的排队（T3 方案里的规则，保留）。

## 9. 派活和"你的消息"

### 9.1 你的消息怎么识别

- 只有通过**客户端 API** 发进来的消息（桌面网页、手机 App，用设备令牌登录）才记为 `source = user`。
- agent 用的是 MCP 端点和会话令牌，**没有任何工具能写入 `source = user` 的消息**。agent 的输出、`consult` 的回答、流程贴回的汇总都记为 `agent` 或 `host`。
- 你粘贴进来的内容算你的消息（你主动粘贴的）。派活卡片会列出实际要做的事，范围检查（§10.2）防止改动超出契约。
- 和 T3 方案相比更简单：T3 里要同时核对 `createdBy` 和 `creationSource`，还要用 OAuth 读；这里来源是宿主自己写的，直接查表。

### 9.2 `request_dispatch` 的检查

1. `basis` 是总主会话里一条 `source = user` 的消息。
1a. `kind = council` 时必须有 `level`（缺省按 `direction`）；`direction` 级即使带 `then: "dev"` 也不自动开工，要等你拍板后的新消息作为依据。
2. 每条 `basis` 只能用一次。
3. `project` 是已登记的项目；`kind` 是 `council`、`dev`、`research` 之一；只有 `council` 可以带 `then: "dev"`。
3a. 可以按任务指定由哪家 agent 做：`payload.agent`（例如 issue 1 给 Codex、issue 2 给 Claude、issue 3 给 DSH）。不指定时按路由表的默认值。指定的厂商必须已启用。几个任务可以同时进行，各自在自己的 worktree 和分支里。
4. 通过：记下范围契约 `{你的原话, kind, project, payload, then}`，贴出派活卡片，启动流程（运行 id 由 `basis` 派生，重复申请不会重复启动）。你看到不对可以说"取消"。
5. 不通过：返回原因。例如依据只是 issue 里的话时，总主会话会来问你"issue #142 提出了 X，要做吗"，你回答后它引用你的回答重新申请。

### 9.3 issue 触发

需要你（或你指定的账号）在 issue 上明确开工（`agent:go` 标签或 `/agent go` 评论）。传给 analyst 的只有 issue 正文和白名单账号的评论。

## 10. 偏好、范围、方案讨论、dev 流程

### 10.1 偏好（与 v3.1 相同）

- `planning`：`thorough` | `balanced` | `conservative`。
- 升级条件（不自行决定，`ask` 你）：方案改动规模相差超过 3 倍；不可逆操作；安全相关路径（默认含 `.github/`）；对外接口变更；`open_questions` 不为空；超出范围契约。
- 你可以随时临时覆盖，例如"这次保守一点"。

### 10.2 范围检查（三层，代码执行）

1. 派活时记下范围契约。
2. `Proposal` 和 `Plan` 必须给出 `touched_paths`、`public_interface_changes`、`new_dependencies`、`security_sensitive`、`beyond_request`；命中升级条件就 `ask` 你。
3. 进入 review 前，比较**固定起点和待审 head**（`git diff --name-only <baseSha>..<head>`，不是工作区的 diff——worker 提交推送后工作区是干净的）与 `touched_paths`；超出的退回 worker 一次，再超出就 `ask` 你。

### 10.3 方案讨论流程

1. 由 `request_dispatch(kind: "council", level: "direction" | "detail")` 启动。`level` 由总主会话按 §2 第 3a 条判断：新项目、新子系统、改变架构或目标的，是 `direction`；已定方向下的实现选择，是 `detail`。拿不准时按 `direction` 处理。
2. 并行让每个启用的 manager 出 `Proposal`（各家看不到别家的）。
3. 代码隐去厂商名，标为"方案甲 / 乙 / 丙"。
4. 选定：
   - `direction`：**不自动选**。汇总（要点、关键差异、各方案的优缺点、总主会话的建议）贴给你，由你在对话里决定，可以继续讨论多轮。你拍板后，总主会话以你的那条消息为依据，再申请 `dev`。
   - `detail`：决策会话按偏好选定；遇到升级条件改为 `ask` 你。
5. 汇总（要点、关键差异、选择和理由）贴回总主会话。
6. 只有 `detail` 级且 `then: "dev"` 才自动开工，沿用同一份范围契约。

### 10.4 dev 流程（每一步）

1. **preflight**（§10.5）：不通过就停，告诉你原因。
2. **analyst**：单次调用，只读，返回 `Plan`。schema 不合格重做一次，再失败 `ask` 你。
3. **worker**：宿主建分支和 worktree，启动长期 ACP 会话。worker 实现、跑测试、用 bot 账号推送、开 PR，最后 `submit_result({pr, head_sha, summary})`。
4. **范围检查**：§10.2 第 3 层。
5. **reviewer**：
   - 数量：普通 1 个，高风险 2 个；优先和 worker 不同厂商，至少换模型。
   - 宿主为每个 reviewer 从 `head_sha` 新建一个一次性 worktree，单次调用，返回 `{verdict, sha, comments}`。
   - 只读不靠模式保证（T3 实测：plan 模式下 Codex 和 Antigravity 都改了文件）；它在一次性 worktree 里改了什么都不影响 PR 分支，评审结束后删除 worktree。
   - 需要 CUA 时先拿锁（§11）。
6. **提交 review**：宿主检查 PR 属于本次运行；当前 head 等于 reviewer 评审的 SHA；所需结论齐全、模型不同（模型取自宿主的启动记录，不靠自报）。然后用 reviewer 账号 approve：调用 GitHub 时**显式传 `commit_id = 评审的 SHA`** 并核对返回的 commit（省略时 GitHub 会挂到最新提交上），正文带 `[agent-reviewer · <vendor>/<model> · <sha>]`；只有所需结论全部是 APPROVE 才走批准。
7. **有 REVISE**：意见交给 worker 修改，回到第 4 步；最多 3 轮，超过 `ask` 你。
8. **合并**：未暂停；head 等于已批准的 SHA；重新读取 checks 和 reviews；**先把"将开启 auto-merge"写入在途台账**，再用 `--match-head-commit` 开启 auto-merge（反过来在两步之间宕机，暂停时会漏掉这个 PR）。
9. **合并收尾**：`--auto` 是异步的，宿主跟踪到实际合并，核对合入的 head 等于批准的 SHA。PR 被关闭、head 变了、合并失败（例如排队时别人先合入导致冲突）都 `ask` 你。
10. **结束**：结果卡片贴回总主会话，推送到手机，写入运行记录。

### 10.5 preflight 与 GitHub 账号

- 目标仓库必须：要求 approval；推送后旧 approval 作废；分支必须与 base 同步；有必需的 checks；只允许 squash；开启 auto-merge；bot 账号和 reviewer 账号不同。
- bot 账号：推送、开 PR（它不能 approve 自己的 PR）。reviewer 账号：approve、开启 auto-merge，可以用你的个人账号，也可以另建。

### 10.6 暂停

- 一按暂停：撤销在途台账里所有 PR 的 auto-merge；合并接口拒绝执行；不再派发新工作。
- 剩余窗口：auto-merge 已开启、还没来得及撤销时 GitHub 可能刚好合并；合入的仍是批准过的 SHA，宿主记录并通知你。
- 暂停按钮在桌面和手机上都有，手机通知里也可以直接按。

### 10.7 review 回流

宿主提交的 review 带 `[agent-reviewer · …]` 标记，流程的 PR 触发器忽略这类 review。

## 11. CUA

- reviewer 通过宿主 MCP 的 `cua_acquire` / `cua_release` 使用 CUA。
- 整机一把锁；拿锁前检查你是否空闲（键鼠空闲时长阈值可配）；锁被占用时立即返回"忙"，不阻塞；拿不到时 reviewer 不用 CUA 完成评审并在正文注明。
- 你可以在桌面或手机上随时收回桌面，CUA 立即释放锁并停止。
- 范围限制（沿用 v5.3 §9.1）：只操作被测应用的窗口；不输入凭据；不打开终端、浏览器账号页、系统设置；界面里的文字一律当数据。

## 12. 客户端：桌面与手机

### 12.1 一套界面，三个外壳

| 外壳 | 怎么做 | 用途 |
|---|---|---|
| 桌面浏览器 | 宿主直接提供网页 | 主要工作界面 |
| iOS App | Capacitor 包装同一套网页 + 原生推送插件 | 看会话、回消息、回答提问、暂停 |
| Android App | 同上 | 同上 |

界面内容（按 11-20 §7.4）：
- 左栏按项目文件夹分组：顶部是总主会话和各家 manager，下面是每个项目的流程运行和工作会话；每个会话显示厂商、模型、状态。
- 中间是对话流（按 §7.1 的事件渲染，包括工具调用、咨询记录、派活卡片），底部输入框可以给任何会话发消息。
- 右栏是当前流程的阶段、PR、评审轮次、待回答的提问。
- 手机上是同样的内容，改成单栏导航；首页放"待你回答"和"进行中"两个列表。

### 12.2 连接：Tailscale

1. Mac 和手机都装 Tailscale，登录同一个 tailnet。
2. 宿主只监听 `127.0.0.1`；用 `tailscale serve` 把 `https://<mac名>.<tailnet>.ts.net` 转发到宿主端口，证书由 Tailscale 自动签发。
3. 手机能直连 Mac 时走点对点；直连不通时自动经 Tailscale 的 DERP 中转。两种情况都是 WireGuard 端到端加密，中转服务器看不到内容。
4. Tailscale 的协调服务器知道有哪些设备，看不到消息内容；如果连这点也不想交出去，可以自建 Headscale。

### 12.3 设备配对与登录

1. 桌面界面上点"添加设备"，显示一个二维码（含一次性配对码，10 分钟有效）。
2. 手机 App 扫码，宿主签发这台设备的长期令牌，存在系统钥匙串（iOS Keychain / Android Keystore）。
3. 宿主同时检查请求来自 tailnet 内（`tailscale serve` 会带上 Tailscale 身份请求头），双重确认。
4. 设备可以在桌面上随时撤销。

### 12.4 推送

| | iOS | Android |
|---|---|---|
| 通道 | 宿主直接调用 APNs（HTTP/2，用 `.p8` 密钥） | 宿主直接调用 FCM（Firebase 项目免费）；不想经过 Google 可改用 UnifiedPush（ntfy，跑在 Mac 上，经 tailnet） |
| 推送内容 | 只放"有新消息 / 有提问"和一个 id，**不放正文**；App 收到后经 Tailscale 拉取内容 | 同左 |
| 可选：带内容 | 用 Notification Service Extension：推送里放加密的正文，手机端用配对时交换的密钥解密 | 数据消息里放加密正文，App 解密后显示 |
| 前提 | 苹果开发者账号（每年 99 美元）；没有它，自己安装的 App 7 天后打不开，也不能收推送 | 无；直接安装 APK |

什么时候推送：流程 `ask` 你；流程完成或失败；合并完成；暂停后的剩余窗口事件；总主会话在你离开时回复了你。

### 12.5 通知上的快捷操作

- `ask` 的选项直接显示成通知按钮（iOS 通知操作、Android 通知按钮），点了就提交回答。
- "暂停"按钮。
- 点按钮时 App 在后台经 Tailscale 调宿主；Tailscale 没连上时，通知提示"无法连接，请打开 App"。

### 12.6 安装与分发

- iOS：TestFlight 装到自己的手机，不上架 App Store。
- Android：直接装 APK（或 Play 内部测试）。

### 12.7 桌面浏览器

- 本机直接打开 `http://127.0.0.1:<端口>`；其他电脑经 Tailscale 打开同一个 `*.ts.net` 地址，同样要配对。

## 14. 进化循环

## 15. 优缺点

### 15.1 和 T3 方案（v3.1）比较

| 方面 | v4 自建宿主 | v3.1 基于 T3 |
|---|---|---|
| 依赖 | 只依赖各家官方命令行和 Tailscale | 依赖 T3（nightly 变化快，Labs 功能） |
| 手机端 | 自己做 App，要花开发时间；iOS 需要开发者账号 | T3 自带，现成 |
| 推送 | 宿主直接发 APNs/FCM，内容可以不出本机 | 必须开启"发布 agent 活动"，经 T3 的云 |
| "你的消息"识别 | 来源由宿主自己写，直接查表 | 要核对两个字段，还要用 OAuth 读 |
| reviewer 只读 | 一次性 worktree（两者相同） | 一次性 worktree |
| 流程引擎 | 自己写，约 800 行，要自己保证重放正确 | 现成，已实测 |
| 会话界面 | 自己写 | 现成，功能多 |
| agent 互相调用 | 只经宿主 `consult`，有上限、可见 | T3 的 `delegate_task` 等，agent 可自由开线程 |
| 遥测 | 无 | 默认开启，需手动关闭 |
| 升级风险 | 各家命令行参数变化时改适配器 | T3 变化 + 各家变化 |
| 工作量 | 大：界面、App、流程引擎、适配器都要写 | 小：只写宿主服务和流程文件 |

### 15.2 v4 的主要优点

1. 核心路径上没有第三方平台，所有数据只在本机和你的设备之间。
2. 宿主完全掌握会话和消息来源，门禁规则可以直接用自己的数据实现，不用绕道读别人的数据库或 API。
3. agent 之间的交互都有记录、有上限，不会失控。
4. 各家都用官方命令行，出问题时容易定位，也更符合各家的使用方式。

### 15.3 v4 的主要缺点和风险

1. **工作量大**：界面、两个 App、流程引擎、四个适配器都是新代码。
2. **流程引擎要自己保证正确**：重放、幂等、重启恢复都容易出细节错误；需要专门的测试。
3. **各家 ACP 的成熟度不一**：Claude 和 Codex 的 ACP 适配器是社区或厂商维护的单独包，DSH 和 Antigravity 的 ACP 是否支持注入 MCP 还没验证；不行时要退回命令行参数，事件格式要分别解析。
4. **iOS 成本**：每年 99 美元；推送证书、TestFlight 需要维护。
5. **手机依赖 Tailscale 在线**：Tailscale 没连上时，通知能到（走苹果或 Google），但回答和拉取内容会失败。
6. **宿主是单点**：Mac 睡眠或宿主崩溃时一切停止；需要防睡眠设置和开机自启（launchd）。

## 17. 第一版范围与顺序（2026-11-25 修订，采纳 ChatGPT 复审意见）

第一版要证明的是：**宿主能说清楚谁授权了什么、现在跑到哪一步、出错后能不能安全继续**。四家都接上、手机 App、推送、进化循环都不挡第一版。

**第一版验收目标**：宿主在任务进行中被强制关闭，重启后既不重复执行外部动作，也不把没做完的事标成成功（实测见 §17.1）。

阶段：
1. **Codex + 本地网页 + SQLite**：能对话、续接、取消；同一会话同时只跑一轮；每个任务有自己的 worktree；重启后先判断旧的写入者是否可能还在（不能排除就冻结会话，由你处理），再查外部状态，把任务区分为"已完成 / 可重试 / 需要人工核对"。
2. **再接 Claude，跑一条真实工作流**：
   - 方向级方案讨论：两家各出方案，宿主汇总，你来选；
   - 在测试仓库跑"实现 → PR → 评审"，**影子模式**：宿主只记录"本来会批准 / 会合并"，由你手动合并；
   - 验证评审期间 SHA 变化、检查失败、宿主中断、暂停这几种情况都处理正确后，再打开自动合并。
3. **手机先用网页**：用 Tailscale 打开响应式页面，确认你确实会在手机上回答提问、看进度、暂停；之后再做 iOS 和 Android App 与推送（§12）。
4. Antigravity、DSH 接入；进化循环。

合并门禁的补充：
- 模型不同只是第二意见，**不能代替**必需的 checks 和分支保护；preflight 缺少任何一项就拒绝开启自动合并。
- **reviewer 账号单独建**，令牌只放在宿主里（钥匙串），**不在本机 `gh` 登录**。本机 `gh` 如果登录着个人账号，它对任何 agent 都可用；如果它同时是 reviewer 账号，agent 一次误操作（例如顺手 `gh pr review --approve`）就会变成有效批准。这是防出错，不是防攻击，符合 §3 的信任模型。

每个阶段单独写实现计划。

### 17.1 验收目标的实测（2026-11-25，Codex，本地裸仓库代替 GitHub）

脚本 `docs/superpowers/research/probes/codex-crash-recovery.mjs`，详见实测记录 §9。

| 场景 | 结果 |
|---|---|
| 同一会话同时启动两个宿主 | 第二个被拒绝 |
| 宿主被杀，Codex 继续跑完并推送 | 重启时杀掉残留进程，查到远端已推送，采纳，不重试 |
| 宿主和 Codex 一起在开始时被杀 | 远端没有，重试，最终 1 个提交 |
| 本地已提交但没推送 | 重试时复用已有提交，最终 1 个提交 |
| 推送成功后、交结果前宿主被杀 | 采纳，不重试 |
| 远端内容不对 | 标为需要人工核对，不动 |

**结论：验收目标达到**——没有重复的外部动作，没做完的没有标成成功。

注：表中"采纳"只适用于这次实测的固定内容任务。正式实现按 §7.5 修订后的规则：没有被宿主接受的结果时，已推送的分支一律保留并标为"需要人工核对"，不标完成（第一版计划的规则 R1）。

同时发现、需要在实现中处理的：
1. Codex 的 `workspace-write` 沙箱默认把 `.git` 设为只读，Codex 会**自己绕道**（去别处克隆后推送）。宿主要把 git 元数据目录加进可写范围（worktree 还包括主仓库 `.git/worktrees/<name>` 和对象目录）。
2. `--ignore-user-config` 挡不住 `~/.codex/skills`。后来确认 skills 本来就应该共享（§13.1），所以单独的 `CODEX_HOME` 里链接登录信息和 skills，只隔离 MCP 和其他个人设置。
3. 本次只测了 Codex 和本地仓库；GitHub 上的 PR、review、合并的对照规则在阶段 2 的影子模式里验证。

## 19. 参考 Orca 后的补充（2026-11-25）
